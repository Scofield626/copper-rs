# Fuzzing `cu_ahrs`, `cu_apriltag`, `cu_aligner`

`cargo-fuzz` (libFuzzer) harnesses for three Copper task components. Every target
runs under AddressSanitizer, so memory errors inside the AprilTag C library are
caught as well as Rust panics.

## Running

The `apriltag-sys` C sources do not compile under GCC's C23 default, so
`.cargo/config.toml` pins `CFLAGS=-std=gnu17`. Nothing extra to export.

```sh
cd fuzz
cargo +nightly fuzz list
cargo +nightly fuzz run <target> -- -max_total_time=300
```

Two flags come up often:

* `apriltag_process` needs `-detect_leaks=0` to look for anything other than
  finding 6, which fires on every run. It clamps `bits_corrected` to 0..=1 on
  purpose: at 3 the detector alone costs gigabytes (finding 7), which would
  OOM-abort the target for reasons unrelated to the code under test.
* `--features unbounded_decode` removes the byte limit on the bincode configs in
  `aligner_buffer` and `apriltag_codec`. That is how findings 4 and 5 reproduce;
  the default limit keeps them from masking everything else.

## Targets

| Target | Component | What it drives |
| --- | --- | --- |
| `ahrs_process` | cu_ahrs | `CuAhrs::process` over arbitrary configs and IMU/mag streams |
| `ahrs_freeze_thaw` | cu_ahrs | `Freezable::thaw` from arbitrary snapshot bytes, then a normal update |
| `aligner_buffer` | cu_aligner | `TimeboundCircularBuffer` push/purge/window plus its freeze/thaw codec |
| `aligner_task` | cu_aligner | the task generated by `define_task!`, full `preprocess` + `process` lifecycle |
| `apriltag_codec` | cu_apriltag | `AprilTagDetections` bincode `Decode` and the hand-written serde impls, incl. the parallel-array invariant |
| `apriltag_process` | cu_apriltag | `AprilTags::process` on well-formed images of arbitrary geometry and content |
| `apriltag_image_decode` | cu_apriltag | `AprilTags::process` on a `CuImage` restored through `Decode`, which skips `CuImage::new`'s asserts |

`bits_corrected_probe` is not a fuzz target; it is a plain binary that measures
finding 7. Run it with `cargo run --release --bin bits_corrected_probe`. It forks
a child per measurement, because the detector leaks (finding 6) and `VmHWM` is a
monotonic high-water mark — measuring in one process makes every configuration
after the first large one report zero growth.

## Oracles

Beyond "does not panic", the targets assert real invariants:

* **ahrs** — finite input must give a finite pose and finite filter state; after
  `thaw`, `sample_period`/`kp`/`ki` must be inside the ranges the thaw code
  clamps to, and the orientation must actually be a unit quaternion.
* **aligner** — the buffer never exceeds its const capacity; `purge(h)` leaves
  nothing older than `h`; `iter_window(a, b)` yields nothing outside `[a, b]`;
  freeze/thaw round-trips.
* **apriltag** — no array exceeds `MAX_DETECTIONS`; `ids`, `poses` and
  `decision_margins` come back the same length (this is what caught finding 8);
  bincode round-trips.

The `purge` oracle only applies when the fuzzer picks sorted input, because
`TimeboundCircularBuffer` documents "assumed to be sorted by time with non
overlapping ranges" as a precondition. See "Not a defect" below.

# Findings

Ten defects. Two are fixed by PR #3 (both in `cu_aligner`); this branch is based
on `master`, so both still reproduce here. The rest are documented with a
reproducer so they can be triaged separately.

## 1. `cu_aligner` panics on a timestamped message with no payload — fixed by PR #3

**Where:** `components/tasks/cu_aligner/src/lib.rs:99` (before the fix)

```rust
output_payload.$index.fill_from_iter(
    tuple_of_iters.$index.map(|msg| msg.payload().unwrap().clone())
);
```

**What happens:** a Copper message carries a time-of-validity and an
`Option<payload>`. A task that had nothing to emit on a given tick still
produces a message: it has a `Tov` but `payload == None`. `process` pushed that
message into the alignment buffer unconditionally. `iter_window` selects on the
`Tov` alone, so the message came back out, and `unwrap()` aborted the process.

**Why it matters:** this is not malformed input. Sparse streams are the normal
case for an aligner — aligning a 10 Hz lidar against a 100 Hz IMU means most
ticks have nothing on one input. The whole robot dies on a `None`.

**Reproducer:** `cargo +nightly fuzz run aligner_task
artifacts/aligner_task/crash-1bd5a50cad4f625a22ae81df140ec5e52735bfab`
The minimised case is a single tick: one input with `Tov::Range(0, 0)` and no
payload, one input with nothing at all.

**Fix:** `process` no longer buffers a message that has no payload — it carries
no data to align, so it should neither occupy a slot in the fixed-size buffer nor
advance the alignment window. `fill_from_iter` also uses `filter_map` instead of
`unwrap`, because `TimeboundCircularBuffer::push` is public and a caller can
still push whatever it likes. Regression test:
`test_aligner_tolerates_payload_less_ticks`.

## 2. `cu_apriltag` reads out of bounds from an unvalidated `CuImage`

**Where:** `components/tasks/cu_apriltag/src/lib.rs:176` in `image_from_cuimage`

**What happens:** `CuImage::new` guards its invariant with two asserts —
`format.is_valid()` and `format.required_bytes() <= buffer.len()`. `CuImage`'s
`Decode` impl (`components/payloads/cu_sensor_payloads/src/image.rs:202`) does
neither; it reads `seq`, `format` and `buffer_handle` and returns the struct. So
a `CuImage` restored from a `.copper` log, a resim keyframe, or a bridge payload
can declare geometry that has nothing to do with its buffer.

`image_from_cuimage` then builds a raw `image_u8_t` pointing straight at the
buffer, copying `width`, `height` and `stride` verbatim, and hands it to the C
detector, which reads `height * stride` bytes.

**Why it matters:** memory unsafety reachable from recorded data. The `unsafe`
block carries a comment about avoiding a double free, but nothing about buffer
length — the invariant it relies on is enforced only in a constructor that this
path never calls.

**Reproducer:** `cargo +nightly fuzz run apriltag_image_decode
artifacts/apriltag_image_decode/crash-b10070d8cc71a2c75f64d0f99f8be238f747357a`

```
SUMMARY: AddressSanitizer: SEGV apriltag-src/common/image_u8.c:495 in image_u8_decimate
```

A 99x39 image with stride 110 and an empty buffer is enough.

**Suggested fix:** validate in `AprilTags::process` before the `unsafe` block —
reject the frame if `format.required_bytes() > buffer_len` or `!format.is_valid()`
— and/or make `CuImage::decode` enforce the same invariant `CuImage::new` does.

## 3. `cu_ahrs` `thaw` can produce a degenerate orientation, then NaN

**Where:** `components/tasks/cu_ahrs/src/lib.rs:307-316`

```rust
let valid_quat = quat.iter().all(|v| v.is_finite())
    && !(quat[0].abs() < 1.0e-12 && ... );
let orientation = if valid_quat {
    UnitQuaternion::new_normalize(Quaternion::new(quat[0], quat[1], quat[2], quat[3]))
} else {
    UnitQuaternion::identity()
};
```

**What happens:** the guard checks that the components are finite and not all
near zero. It does not check that normalisation can succeed. For components
around `5e33` — finite, well inside `f32::MAX` — the *sum of squares* overflows
to infinity, `new_normalize` divides by infinity, and the result is
`(0, 0, 0, 0)`. That is not a unit quaternion, but it is now wrapped in a
`UnitQuaternion`, which the rest of nalgebra trusts.

The next ordinary IMU sample then yields `roll = NaN`:

```
thaw left a non-unit orientation (norm^2 = 0)
... roll: NaN, pitch: -1.5707964, yaw: 0.0
```

Note the contrast with the surrounding code: `sample_period_s`, `mahony_kp` and
`mahony_ki` are all clamped to explicit ranges just below. `filter.bias` is only
checked for finiteness, never bounded, which is a second instance of the same
gap.

**Why it matters:** every field this function restores comes from a log file. A
NaN attitude propagates silently into every downstream controller.

**Reproducer:** `cargo +nightly fuzz run ahrs_freeze_thaw
artifacts/ahrs_freeze_thaw/crash-nonunit-quaternion`

**Suggested fix:** normalise, then verify the result is finite and unit-norm;
fall back to identity otherwise. Clamp `bias` to a plausible rate.

## 4. `cu_apriltag` — unbounded allocation decoding `AprilTagDetections`

**Where:** `core/cu29_runtime/src/payload.rs:143` in `CuArrayVec::decode`,
reached from `components/tasks/cu_apriltag/src/lib.rs:46`

```rust
let inner = Vec::<T>::decode(decoder)?;   // allocates the declared length
let actual_len = inner.len();
if actual_len > N { return Err(ArrayLengthMismatch { .. }) }
```

**What happens:** the length bound is checked *after* the whole `Vec` has been
allocated. The runtime decodes with `NoLimit`, so the declared length is
attacker-controlled and unbounded. Eight bytes of log request a 5 GB allocation:

```
ERROR: libFuzzer: out-of-memory (malloc(5255018808))
```

**Why it matters:** `AprilTagDetections` is a logged payload, so this is
reachable from any recorded or bridged data. It is a `cu29` core issue that
`cu_apriltag` inherits — every `CuArrayVec` payload in the tree has it.

**Reproducer:** `cargo +nightly fuzz run apriltag_codec --features
unbounded_decode artifacts/apriltag_codec/oom-cuarrayvec-unbounded --
-malloc_limit_mb=512`

**Suggested fix:** decode the length first, reject `len > N` before allocating,
then read elements into the `ArrayVec` directly.

## 5. `cu_aligner` — unbounded allocation in the snapshot codec — fixed by PR #3

**Where:** `components/tasks/cu_aligner/src/buffers.rs:52` (before the fix)

```rust
let bytes: Vec<u8> = Decode::decode(decoder)?;
```

**What happens:** `freeze` writes each buffered message as a length-prefixed byte
blob. `thaw` read it back with `Vec::<u8>::decode`, which allocates the declared
length up front. `thaw` does bound the *number* of messages against `S`, but
nothing bounded the size of each one. A corrupted keyframe aborts the process
with `capacity overflow` from `raw_vec`.

**Why it matters:** same shape as finding 4, and it defeats the length check that
is already there two lines above.

**Reproducer:** `cargo +nightly fuzz run aligner_buffer --features
unbounded_decode`

**Fix:** three changes, all in `decode_buffered_msg`.

* A per-message cap, `MAX_MSG_SNAPSHOT_BYTES` (256 MiB), rejects an absurd
  declared length before anything is allocated. `encode_buffered_msg` refuses to
  write a snapshot above the same cap, so `freeze` can never produce something
  `thaw` would reject.
* The blob is read in 8 KiB chunks instead of being allocated in one go, so a
  length the stream cannot satisfy fails on end-of-input having allocated one
  chunk rather than the full claim.
* The *inner* decode of the blob gets a limit (`MAX_MSG_CLAIM_BYTES`) rather
  than the default `NoLimit`. Without this the outer fix is not enough: a field
  inside the snapshot declares its own length, and the fuzzer went straight back
  to `malloc(1862396544)`.

The two caps are deliberately different. Bincode's limit counts *claimed* bytes,
not wire bytes — `Decoder::claim_container_read` claims `len * size_of::<T>()`,
so a `Vec<u64>` of small varints claims about eight times what it occupies on the
wire. Bincode has no encoder-side limit to make the two agree, so a payload
holding an enormous collection of multi-byte elements could in principle be
frozen and then refused on thaw. Both caps sit far above any realistic buffered
message; the asymmetry is documented on the constants.

The wire format is unchanged — bincode encodes a `Vec<u8>` as a `u64` varint
length followed by the raw bytes, which is byte for byte what the chunked reader
consumes. Regression tests: `thaw_rejects_a_bogus_message_length` (both the
above-cap and the truncated case) and `freeze_thaw_round_trips`.

**Residual:** a snapshot can still force a single allocation up to the claim
budget. Bincode's limit is a const generic, so it cannot be set to the blob's
actual length. The real fix belongs in the runtime, which should not decode
keyframes with `NoLimit` at all — that is what makes finding 4 exploitable too.

## 6. `cu_apriltag` leaks memory on every frame

**Where:** `components/tasks/cu_apriltag/src/lib.rs:176-183`

```rust
let ptr = Box::into_raw(low_level_img);
ManuallyDrop::new(Image::from_raw(ptr))
```

**What happens:** the `image_u8_t` header is boxed, leaked with
`Box::into_raw`, and the `Image` that owns it is wrapped in `ManuallyDrop` so it
is never dropped. The `ManuallyDrop` correctly stops AprilTag from freeing
Copper's pixel buffer, but nothing ever reclaims the header. LeakSanitizer:

```
Direct leak of 24 byte(s) ... in image_from_cuimage lib.rs:176
Direct leak of 72 byte(s) ... in AprilTags::new lib.rs:238   (the Family)
```

24 bytes per frame is roughly 62 MB/year at 30 fps — small, but unbounded, and
robots run for a long time. The 72-byte `Family` leak is once per task.

**Reproducer:** `cargo +nightly fuzz run apriltag_process` (leak detection on,
which is the default).

**Suggested fix:** keep the `Box` alive in a field or reconstruct and drop it
after `detect` returns, rather than leaking it.

## 7. `cu_apriltag` takes `bits_corrected` from config with no bound

**Where:** `components/tasks/cu_apriltag/src/lib.rs:226`

```rust
let bits_corrected = config.get::<u32>("bits_corrected")?.unwrap_or(1) as usize;
```

**What happens:** the value goes straight into `add_family_bits`, and the
AprilTag quick-decode table grows combinatorially in it. Measured with
`cargo run --release --bin bits_corrected_probe`:

| family | bits=1 | bits=2 | bits=3 |
| --- | --- | --- | --- |
| tag36h11 | 0.2 ms | +12 MB, 11 ms | +1.2 GB, 323 ms |
| tagStandard41h12 | 0.9 ms | 61 ms | +5.3 GB, 1.66 s |
| tagCustom48h12 | 53 ms | 1.8 s | did not complete |

**Why it matters:** a one-character config typo makes the app allocate gigabytes
during startup and get OOM-killed, with no diagnostic pointing at the config.
`cu_ahrs` clamps every value it reads from config; `cu_apriltag` clamps none of
`bits_corrected`, `tag_size`, `fx`, `fy`, `cx`, `cy`.

**Suggested fix:** clamp `bits_corrected` to 0..=2 and return a `CuError` naming
the key when it is out of range.

## 8. `cu_apriltag` — `Decode` desynchronises the three parallel arrays

**Where:** `components/tasks/cu_apriltag/src/lib.rs:44-55`

`AprilTagDetections` holds three arrays — `ids`, `poses`, `decision_margins` —
where entry `i` of each describes one detection. Everything that reads the type
relies on that: `filtered_by_decision_margin` zips all three, and `Serialize`
declares `ids.len()` as the tuple length.

`Decode` reads the three as independent `CuArrayVec`s and never checks that they
came back the same length, so a crafted log yields e.g. `ids=1, poses=0,
margins=0`. The zip in `filtered_by_decision_margin` then silently reports zero
detections while `ids` says there was one, and `Serialize` declares a tuple of 1
element and writes 0 — malformed output for any format that trusts the declared
length.

**Reproducer:** `cargo +nightly fuzz run apriltag_codec
artifacts/apriltag_codec/crash-3c585604e87f855973731fea83e21fab9392d2fc`

**Suggested fix:** have `Decode` reject the value when the three lengths differ.

## 9. `cu_apriltag` — unbounded push in `Deserialize`, and a panicking `Serialize`

**Where:** `components/tasks/cu_apriltag/src/lib.rs:92-109` and `:59-76`

`visit_seq` loops `while let Some(..) = seq.next_element()?` and pushes into
`ArrayVec<_, 16>` with no bound check. `deserialize_tuple(MAX_DETECTIONS)` keeps
bincode within 16, which is why the `apriltag_codec` target does not trip it —
but a self-describing format (RON, JSON) is free to ignore the length hint and
feed more elements, and `ArrayVec::push` panics when full.

Separately, `Serialize` calls `tup.serialize_element(..).unwrap()` inside a
`for_each`, so any serializer error becomes a panic instead of an `Err`.

**Status:** reasoned from the code, not reproduced — reaching it needs a
self-describing serde format, which no target currently drives.

**Suggested fix:** bound the push in `visit_seq` and return
`Err(A::Error::invalid_length(..))` past `MAX_DETECTIONS`; propagate the
`serialize_element` error with `?` instead of unwrapping.

## 10. `cu_aligner` — a message with no time information silently widens the window

**Where:** `components/tasks/cu_aligner/src/buffers.rs:118` and the
`get_latest_aligned_data` arm of `alignment_buffers!`

A message can carry a payload but `Tov::None`. It is still buffered.
`most_recent_time` then returns
`Err("Trying to align temporal data with no time information")` for that whole
buffer — and `get_latest_aligned_data` swallows it with `unwrap_or(None)`, then
`.flatten()` drops it. That stream stops constraining the alignment window until
the message is purged, so the task keeps emitting alignments computed from the
other streams alone.

Such a message can never contribute to the output either: `iter_window` returns
`false` for `Tov::None`. It only takes a slot and suppresses an error.

**Status:** pre-existing, not fixed. The `aligner_task` target generates this
shape but has no oracle for it. Same class as finding 1 — a fix would filter it
at push alongside the payload-less case — but it changes the window semantics
rather than removing a panic, so it was left out of PR #3.

## Not a defect

`TimeboundCircularBuffer::purge` stops at the first message at or after the
horizon, so out-of-order timestamps leave stale messages behind. The type
documents "assumed to be sorted by time with non overlapping ranges", so this is
an unmet precondition rather than a bug, and the `aligner_buffer` purge oracle
only applies to sorted input. It is still worth knowing that nothing enforces the
precondition and `push` accepts anything, since an aligner is exactly where
multi-sensor streams meet.
